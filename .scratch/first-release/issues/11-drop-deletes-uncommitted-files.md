# `drop` permanently deletes files that were never committed

Category: bug
Status: needs-triage

## Problem

The README says dropped files "stay recoverable from the shadow repo's history", but `cmd_drop` runs `rm -rf` on the area whether or not its files were ever committed. With `autocommit` off, or for files created since the last commit, nothing is in history, so the files are gone for good. The command still prints "recoverable from the shadow repo's git history".

## Reproduction (from code review)

With no `autocommit` line, create a per-branch file and run `shadow drop <branch>`. `git -C <shadow> log -- branches/<slug>/` shows 0 commits.

## Notes

Commit the area before deleting it (`git add` + commit "snapshot before drop"), so the promise holds. An alternative is to refuse to drop uncommitted files without `--force`. Committing first keeps the command simple and makes the message true. The same question applies to `promote`, whose `rm -rf "$src"` runs after the files have been moved, so it is less risky.
